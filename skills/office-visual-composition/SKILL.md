# 离线办公视觉编排

这是唯一审美编排入口，与 office-artifacts 的数据/工具流程配合。references 中的上游文档是只读参考，不是另外激活的 skill，不覆盖当前安全边界。不要四套指令并行执行。

## 1. 先写视觉方向

明确受众要作什么决定、阅读距离、中文内容密度、屏幕/打印交付、真正的首要结论。用真实业务内容设计，不伪造指标充当装饰。写下视觉目标和理由，例如“研究报告以论证和注释为主，图表必须支持标题结论”，而非“做一个高级科技风看板”。参考 references/anthropic-frontend-design.md 的主题、排版与信息结构原则；忽略其中联网字体和超出本引擎能力的实现建议。

## 2. 有界本地参考检索

先查 office_capabilities，确认 office_design_reference 支持的调用字段。依次按需要查 style、typography、color、chart、landing、product、ux、web，传 query、domain、limit（1–5）。最多选与当前问题有关的几个域，不为凑数全部查询。典型关键词：editorial、enterprise dashboard、comparison、trend、accessible。中文需求可明确翻译成英文检索词，保留原意。记录返回的 commit、CSV 和 entry，以及采用/拒绝的理由。

查不到时说明没有匹配，依据内容手工规划，不随机套色。检索结果只是设计参考，不是评审结论。禁止执行上游安装器、persist、任意输出路径、联网检索服务、遥测和外部字体/npm/CDN。字体只用返回的系统 CJK fallback；不能声称指定字体在用户机器一定存在。

## 3. 比较两种构图，再选一个

生成内容层面的两种草图计划：每种说明首屏视觉焦点、阅读路径、主图与证据的位置、正文密度及窄屏重排。示例：经营分析可比较“结论→主趋势→驱动分解”和“异常清单→对比图→处置”；研究报告可比较“论点→证据→限制”和“对照双栏→综合结论”。以任务和真实数据取舍，不以卡片数、彩色面积、DOM 节点数或统一组件数量评分。

## 4. 定义 tokens 与数据叙事

记录背景/正文/强调/风险色的语义、标题与正文字级及字重、中文行高/段落间距、内容宽度、列对齐、分组留白和边线用途。用大小、位置、留白建立主次，不靠全页加粗和彩色卡片。长标题换行要有节奏；数字用一致的小数位和单位；打印不依赖浅色底纹。

对每幅图写一句“读者应看到什么”：趋势用一致时间轴，比较用共同基线，分布体现范围，构成只在有可靠总量时使用。标清来源、日期、单位、缺失、预测与不确定性。趋势/类别不能仅靠颜色辨识。保留可读标签与数据表，避免把所有图塞到同一尺寸。

## 5. 映射到真实 HTML 能力

查 office_capabilities 的可执行示例，再映射到支持的 spec 字段。不能把视觉计划中不存在的布局字段直接塞给引擎。若引擎无法表达关键构图，明确限制并选有理由的可执行替代，不偷偷回退到统一 KPI 卡片模板。引用 references/vercel-web-interface.md 检查语义、键盘、焦点、溢出、可访问标签；这些是可用性检查，不等于审美验收。

## 6. 截图批评与修复闭环

运行 office_validate_html 取得宽屏、窄屏、打印证据。真正打开截图，逐张指出具体区域：第一眼是否读到结论；视觉权重是否符合重要性；中文换行/字体/留白是否合理；图表是否支持叙事；长标签、表格、注释与打印是否仍可读。每项批评附截图路径、视口、观察、修复措施。不要声称 DOM 校验能判断审美。

优先修复内容遮挡、误导图表和错误主次，再修排版节奏。新文件输出，重新验证并对照截图，记录仍存在的不足。没有截图、不能查看图片、工具失败或只完成 DOM 检查时，必须标为 pending-human-review，不可宣称视觉通过。截图已经由能看图的模型审查时可说明“已做视觉复核”，仍不得保证人人喜欢。

## 最小交付记录

交付实际 HTML/Excel、视觉方向、两种布局取舍摘要、采用的参考来源、验证证据及未解决项。不交付虚构美学分数。参考包版本与许可见 references/manifest.json 和 references/ADAPTATION.md；原始上游文件可追溯，当前流程为本项目原创整合。
